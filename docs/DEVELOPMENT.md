# Архитектура и обслуживание

## Процессы

Electron main process запускает собственный Python runtime на случайном loopback-порту. Renderer работает с sandbox, context isolation, без Node.js; доступен только ограниченный IPC. Bearer token остаётся в main process и локальном discovery-файле. API не принимает browser Origin. Приложение не слушает внешние интерфейсы.

Python обслуживает SQLite, очередь и отдельные worker-процессы аккаунтов. Вендорный MCP имеет глобальное состояние, поэтому аккаунты разделены процессами и корневыми папками `accounts/<uuid>/profile`. Cookies и служебные файлы находятся внутри соответствующего аккаунту корня. В один момент выполняется одна браузерная операция приложения.

При подтверждении фиксируются account_id, URL получателей и окончательные тексты. SQLite помечает попытку `sending` до обращения к браузеру. После аварийного завершения `sending` превращается в `unknown`; автоматического повтора нет. По URL действует защита от повторных контактов между кампаниями и аккаунтами. Изменение шаблонов или выбора отменяет незапущенную старую очередь.

MCP-адаптер stdio обращается к этому же локальному API. Он не открывает вторую базу и не выдаёт инструмент первичного подтверждения отправки. Discovery содержит локальный token: это служебный файл, его нельзя включать в экспорт или отправлять в поддержку.

## Браузерный движок

Python Patchright 1.64.4 закреплён точно в зависимости браузерного адаптера и `uv.lock`. Эта поставка содержит драйвер `patchright-core` 1.64.3 и Chromium 156.0.8078.4 (revision 1248): версии Python-обёртки, драйвера и браузера различаются намеренно, согласно метаданным пакета.

Все браузерные пути идут через `BrowserManager` и `patchright.async_api`: ручной вход, поиск, чтение профиля, снимок фотографии для локального OCR, приглашения, проверка связи/переписки, обычное сообщение, Premium InMail и Recruiter. MCP приложения обращается к тем же worker-процессам. OCR обрабатывает полученное изображение локально и не запускает другой браузер.

`diagnostics.browser_engine` показывает фактические версии без открытия LinkedIn. Самопроверка дополнительно запускает встроенный браузер и сверяет его версию с манифестом Patchright. Несовпадение закреплённого пакета или подмена драйвера останавливает worker до открытия аккаунта. В коде Patchright подключается как `patchright_session`, ошибки ожидания называются `BrowserTimeoutError`. Переменная `PLAYWRIGHT_BROWSERS_PATH` остаётся: её читает сам Patchright. Пакетов Playwright нет ни в Python, ни в Node, ни в собранном приложении.

Установленный пакет использует собственную папку браузера и не наследует чужой cache через переменные окружения. Отсутствие встроенного браузера вызывает понятную ошибку переустановки; скрытого переключения на системный Chrome нет.

Темп задаёт один `BrowserPacer` на worker: следующая команда может начаться через случайные 8–14 секунд после завершения предыдущей, включая завершение с ошибкой. Время загрузки страницы не заменяет этот отдых. Переходы `PacedNavigator` и вложенные вызовы браузерного MCP получают паузу 1,5–3,5 секунды; непосредственно перед отправкой приглашения, обычного сообщения или InMail добавляется 2–4 секунды. Затем повторно проверяются адресат, точный текст и условия канала. Первая команда нового worker не ждёт межкомандный интервал. Паузы не добавляются к локальным операциям интерфейса и не предназначены для обхода CAPTCHA. Обнаруженная проверка входа или CAPTCHA останавливает связанные очереди отправителя до ручного действия владельца; случайные интервалы не гарантируют отсутствие проверок и ограничений LinkedIn.

## Хранение

По умолчанию используется Electron userData (`app.getPath('userData')`). Точное имя папки зависит от приложения/платформы. Для изолированных тестов задаётся `BOOSTER_DATA_DIR`; обычному пользователю эта переменная не нужна.

Данные сохраняются в SQLite WAL после каждого изменения. В версии 0.1.1 нет облачного backup, командного сервера, лицензирования или auto-update. Обновлять приложение следует при закрытой очереди с резервной копией SQLite через `sqlite3.Connection.backup`, а не простым копированием одного активного DB-файла без WAL. Сессии аккаунтов в резервную копию профилей рекрутинга не включать.

## Проверки

- `uv run pytest -q`: хранилище, подмена отправителя, невоспроизводимая отправка, пагинация при продолжении, изоляция корней, OCR, авторизация API, безопасный экспорт.
- `npm run test:ui`: настоящее окно Electron и локальный API с вымышленными тестовыми профилями; без LinkedIn-запросов и отправок.
- `uv run python scripts/runtime_smoke.py`: именно собранный исполняемый файл, встроенные Chromium/OCR, настоящий MCP stdio bridge. Синтетический DOM проверяет алгоритм, но не совместимость со всеми вариантами LinkedIn.
- `booster-backend --self-test`: автономная проверка установки без обращения к LinkedIn.

`BOOSTER_BROWSER` предназначен только для контролируемых проверок исходного кода с конкретным браузером под управлением Patchright. Установленный клиентский пакет игнорирует эту переменную и использует встроенный Chromium. Не открывайте существующий профиль более старым браузером.

Node UI-тесты используют закреплённый `patchright` 1.64.3 (`patchright/test`: Electron driver и assertions) с `patchright-core` 1.64.3. Отдельных зависимостей `playwright`, `playwright-core` и `@playwright/test` нет; это проверяет тест зависимостей.

В этой версии драйвера первый Electron renderer остаётся приостановленным: инициализация ждёт настройки renderer до `Runtime.runIfWaitingForDebugger`. `scripts/patchright_test_driver.cjs` перед импортом драйвера автоматически применяет одну поправку только для `browserOptions.name === "electron"`: возобновляет renderer перед ожиданием всех тех же setup promises. Обычный Chromium и Python runtime не меняются. Адаптер проверяет точную версию и SHA-256 исходного/уже исправленного bundle; неизвестное содержимое останавливает тесты. Лицензионные уведомления сохраняются. Повторная подготовка идемпотентна, обновление Patchright требует пересмотра адаптера. Оба UI-скрипта используют его автоматически, включая запуск после чистого `npm ci` и проверку собранного приложения. Адаптер и Node-драйвер относятся только к разработке и не входят в клиентский пакет.

## Сборки

PyInstaller собирается на целевой OS. macOS-пакет этой поставки — arm64; Windows-скрипт — x64. Обновление зависимостей выполняется отдельно с изменением lock-файлов и повторной проверкой. Runtime содержит Python, MCP, OCR-модели и браузер; в клиентском пакете нет требования устанавливать их отдельно.

Папки `.venv`, `node_modules`, `runtime`, `build`, `release`, `.build-tools` генерируются. В исходный архив их не включают. `licenses` сохраняет upstream notices; описание поставки и фактические результаты находятся в RELEASE-STATUS.

Mac-пакеты собирайте в локальном каталоге вне синхронизации File Provider/iCloud либо на отдельном смонтированном APFS-томе. Служебные Finder-атрибуты могут появиться на вложенных `.app` во время копирования. `after_pack.cjs` очищает только эти атрибуты в готовящемся пакете и требует успешную строгую проверку подписи. Выпуск 0.1.3 дополнительно проверен внутри смонтированного read-only DMG.

Перед PyInstaller удаляется только сгенерированный `backend/booster_recruiter.egg-info`: его устаревшая версия могла перекрывать установленную metadata. `runtime_smoke.py` сверяет версию собранного сервиса с `package.json`, чтобы такая несогласованная сборка останавливалась до упаковки.

## Распространение вне магазинов

Публикация в App Store или Microsoft Store не требуется. Для удобного распространения Mac-приложения используется Developer ID и notarization. Локальная ad hoc/неподписанная сборка не заменяет их. Сертификат Apple Development не является Developer ID для передачи клиенту. См. [Apple Developer ID](https://developer.apple.com/developer-id/).

Windows допускает неподписанную сборку, но предупреждения SmartScreen зависят от репутации файла и издателя. Сертификат подписи не гарантирует, что предупреждений сразу не будет. См. [Microsoft Defender SmartScreen](https://learn.microsoft.com/en-us/windows/security/operating-system-security/virus-and-threat-protection/microsoft-defender-smartscreen/).

Для подписанного выпуска сначала нужно проверить и подписать вложенный runtime и browser code, затем приложение, передать его в notarization и проверить ticket/запуск на чистом Mac. Наличие поля `hardenedRuntime` в настройках не доказывает, что такой выпуск прошёл проверку.

## Ограничения LinkedIn

Адаптер читает отрендеренные страницы, не использует приватный Voyager API. Разметка и доступность каналов могут меняться. Реализованы приглашение, ожидание принятия, обычное сообщение и InMail в рамках утверждённого плана. Автоматические follow-up после молчания не реализованы. Офлайн-тесты адаптеров не заменяют приёмку на реальном LinkedIn.

## Автоматизация 0.2.0

`outreach.py` хранит настройки, неизменяемые планы и результаты; `outreach_runtime.py` выполняет только утверждённые планы через общий browser_lock; `outreach_browser.py` реализует ограниченные браузерные адаптеры обычного LinkedIn. Старые таблицы batches/deliveries сохранены для истории и совместимости.

Новые таблицы outreach_runs, outreach_members, outreach_actions не меняют существующие профили/сессии. Перед необратимым действием записывается submitting. При перезапуске оно становится unknown, а получатель требует проверки. Unknown InMail сохраняет предполагаемую стоимость попытки для истории и блокирует повтор до ручного установления результата. После подтверждённого приглашения обновлённый план той же кампании может продолжить ожидание без повторного приглашения.

Планировщик каждые 30 секунд выбирает очередь, у которой наступило время проверки; браузерные проверки выполняются с указанным интервалом, по умолчанию 12 часов. Проверка не запускается параллельно входу или другой операции. Рабочее время считается в часовом поясе кампании. Приложение не применяет собственные дневные лимиты или числовой бюджет InMail: объём задаётся утверждённым списком получателей. Сохраняются разрешения каналов, проверка текущих кредитов LinkedIn и защита от повторных/неизвестных отправок. Старые поля `daily_invites`, `daily_messages`, `daily_inmails`, `inmail_budget` удаляются при нормализации и не ограничивают действия. Сохранённое ожидание именно старого лимита приложения переводится в готовность к следующей проверке; ручная пауза плана и назначенное время проверки сохраняются. Обнаруженное ограничение отправки LinkedIn приостанавливает активные планы подтверждённого отправителя, включая его дублирующие браузерные слоты. Очередь остаётся сохранённой; автоматического повтора до ручного продолжения нет. Это отличается от ограничения доступа к аккаунту: недельный предел приглашений сам по себе не помечает аккаунт как заблокированный.

Бесплатный и платный каналы проверяются отдельно. InMail требует уникального адресата, распознанной формы с темой и положительного текущего баланса. Непосредственно в одной JS-операции перед кликом повторно проверяются тема, канал, баланс, история и закреплённый получатель. Успех подтверждается существующим механизмом нового серверного идентификатора сообщения в соответствующем диалоге.

MCP приложения поддерживает configure_outreach, check_connections, preview_outreach. Утверждение, возобновление плана, проверка «сейчас» и установление результата неизвестной отправки (`outreach.approve`, `outreach.resume`, `outreach.check_now`, `outreach.resolve`, `delivery.resolve`) выполняются только в окне приложения: токен агента получает 403. Текущий набор инструментов описан в разделе рабочего пространства ниже.

При автономных проверках всегда используйте отдельный BOOSTER_DATA_DIR. Никогда не открывайте рабочую SQLite через Store ради анализа: конструктор выполняет восстановление после сбоя. Для диагностического чтения используйте SQLite mode=ro. Работающее окно входа не закрывать и не переподключать до сигнала пользователя.

## Recruiter и мастер настройки 0.2.1

`recruiter_browser.py` читает только отображаемый UI. Переход от публичного профиля к Talent проверяется по обратной публичной ссылке. Контракт и подпись входят в `outreach_runs.context`; доступность сервиса хранится в `account_services`. Стоимость попытки записывается в `outreach_actions.credit_cost`: бесплатный InMail имеет 0, платный 1, старые неизвестные записи учитываются как 1.

Подтверждение берётся из свежей истории после предварительно пустой переписки. В очередь возвращается полный идентификатор конкретного Recruiter-диалога. Проверка ответа читает его сообщения, а не общий ярлык Pending/Accepted. После ручного подтверждения неизвестного исхода диалог восстанавливается только по теме и полному утверждённому исходящему тексту.

`account.recruiter` проверяет контракт и настройки. `account.recruiter_prepare` отключает персональный single-message auto-draft и touch-up; остальные настройки не трогает. `outreach.preview` для Recruiter асинхронно читает реальную подпись и не является разрешением отправки. MCP использует тот же API.

## Видимость браузера 0.2.2

`Worker.call` выбирает видимый процесс только для `interactive: true` и ручного `open_profile`. Изменение режима закрывает stdin предыдущего простаивающего worker, ожидает его выхода и только потом открывает тот же профиль. `Runtime.verify` по умолчанию работает скрыто; ручной вход и подключение Recruiter явно передают интерактивный режим.

Вендорный BrowserManager поддерживает `native_headless`, передаваемый через BrowserConfig. Это обычный нативный headless Chromium с его собственной идентификацией, без macOS hidden target и без подмены user-agent. Благодаря этому рабочее окно не появляется даже кратковременно при запуске.

## Рабочее пространство и MCP

Публичный адаптер предоставляет 17 инструментов. `recheck_attention_item` выполняет отдельную проверку без отправки и без возобновления плана. `get_workspace_attention` читает ответы и причины ручного вмешательства, `list_campaign_templates` читает сохранённые настройки, `create_campaign_from_template` создаёт только новый черновик без получателей и разрешений отправки, `create_workspace_backup` сохраняет локальную копию бизнес-данных. Восстановление доступно только через подтверждение в приложении; инструмента восстановления MCP нет. Браузерные сессии в копии не входят.
